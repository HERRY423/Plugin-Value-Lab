# Plugin Value Lab：从“插件能跑”到“插件值得用”

当前版本：0.5.0。本文保留早期产品取舍，并补充[正向价值指标、样本量规划和结算证据设计](VALUE-METRICS.zh-CN.md)；设计分析不能当作已经完成的用户研究。Epistemic Plugin Arena 仅作为[后续展望](EVIDENCE-LAYERS.md)，不作为当前架构依赖。

## 起点与用途

用户给出的链接指向 Claude Code 官方的 [Plugin evals 文档](https://code.claude.com/docs/en/plugin-evals)，并非一篇能够单独核实内容的社交媒体推文。该产品把插件评估放到真实宿主会话中，以成组任务和评分规则比较有插件、无插件两种条件，并提供结果诊断。这为本项目提供了直接的工作流启发。本文不假定还有一篇未提供链接的推文，也不把下面的设计建议归因于官方文档。

Plugin Value Lab 面向插件作者、团队采购者和研究工作流负责人。它帮助回答一个具体问题：**在明确的任务分布、模型、宿主和资源条件下，这个插件带来的变化是否足以支持继续采用、迭代或进入下一轮评估？**

它适合在发布前寻找退步、对比插件版本、审核已有评测结果，或把“我觉得很有用”变成可以复查的决策材料。它不是自动认证插件商业价值或科学正确性的系统。

## 五个问题必须分别回答

| 层次 | 实际问题 | 合适的证据 | 单独不能说明什么 |
| --- | --- | --- | --- |
| 结构有效 | 宿主能否识别目录和声明？ | 清单、语法和打包检查 | 运行成功、任务质量 |
| 功能有效 | 目标技能或工具能否执行？ | 实际宿主运行、错误与工具轨迹 | 相对基线的增益 |
| 结果增益 | 用户任务是否完成得更好？ | 匹配条件的有/无插件比较 | 成本合理、可推广 |
| 采用效益 | 增益是否抵得过成本和退步？ | 完整费用、时间、质量底线、用户约束 | 市场需求、支付意愿 |
| 外部价值 | 真实用户能否持续受益？ | 独立场景、真实用户、复现和领域评议 | 对所有用户或所有研究都有效 |

这些层次彼此相关，但没有自动升级关系。清单验证通过不等于插件安装成功；本地运行成功不等于在另一宿主工作；局部质量提升不等于真实团队采用后节省人力；科学审阅措辞谨慎也不等于审阅结论正确。

本插件的边界是第三层与第四层的部分决策支持，并为第二层和第五层保留证据入口。它不把自己产生的报告转化为独立认证。

## 为什么无插件基线是产品核心

大模型本来就可能完成任务。若插件条件得到 95 分、基线得到 95 分，插件没有在该任务集上显示质量增益。反过来，插件条件只有 80 分也可能相对 50 分基线有明显帮助，不过仍可能达不到业务最低质量要求。只看插件一侧，无法分清这两种情况。

比较也不仅是两个数字相减。假如插件侧换了更强模型、开放更多工具、获得更多上下文，或者 baseline 读到了插件指导，那么差异的归因就不再清楚。初版要求显式记录条件与会话，检查两侧是否符合被冻结的设计；用户还须核对实际宿主环境，因为自报字段不能独立证明真实隔离。

对插件开发尤其有用的“零增益”有两类：模型已经足够强，插件没有留下提升空间；插件确实触发了，却没有改善最终结果。前者提示寻找更合适的任务边界或降低执行成本，后者提示修改技能内容、工具设计或反馈环节。把二者合并成一个“通过率”会丢掉产品判断。

## 不让流程代替成果

技能触发率、工具调用成功率、输出格式、审阅完成时间都可以是诊断信息。只有当它们本身构成用户验收标准时，才应该作为结果的一部分。例如导出合法 JSON 可以是一个交付要求；“调用过某工具”通常不是用户问题的答案。

因此评分规则显式区分 `outcome` 和 `process`。后者保留在记录里，但不提高质量分。关键结果规则失败可以阻止正向结论，避免十项轻量检查掩盖一个会造成严重错误的核心失败。固定字符串和 JSON 检查适合明确的机械约束；复杂事实、设计合理性和领域正确性需要有依据的人工评议，不能伪装成几条正则就已验证。

## 有益的拒答与无益的拒答

只奖励“更谨慎”会训练出什么都不做的插件；只奖励“总能输出”则会奖励无根据的结论。任务集因此包括普通任务、预期无额外帮助的负对照，以及应当拒绝或暂缓判断的任务。三者都按用户目标评价。

科研示例展示这一点：缺少供体层面的重复时，指出推断限制是一种成功；当用户只请求一个合法的描述性结论时，一概拒绝也是一种失败。这里评估的是证据审阅行为，而非证明任意生物学发现成立。真实研究仍需要原始资料、可解释的方法选择、领域人员裁决和独立复核。

## 质量与成本分别展示

默认报告保留质量差、费用差和缺失项，不用一个看似精确的“价值总分”掩盖权衡。模型费用、工具费用、人工作业时间与等待时间不是可互换的东西。人工时间仅在已有原始计时间隔和明确小时单价时转换为成本。等待 20 分钟并不自动意味着人工投入 20 分钟。

当质量相同而成本更低时，可以讨论效率收益；当质量更高而费用也更高时，需要具体业务愿意接受的取舍。配置里的质量底线、可接受单例退步和成本约束，让决策原则在看见结果之前明确。初版不推算收益、市场规模或支付意愿，因此不会自动输出货币化投资回报率。

实现提供两种预先选择的目标：默认质量目标要求达到正向质量提升阈值；效率目标要求平均质量不下降、达到底线并降低完整成本。两者都不能绕过关键失败和单例退步。这里的“平均质量不下降”只描述提交的案例，不是经统计非劣效性研究证明等效；也不能看过结果后切换目标来取得通过。

## 证据完整性优先于漂亮平均值

超时、错误、中断、跳过、未知人工分数和未知费用都进入记录，不能通过删除“不好看的运行”提升均值。相同任务的多次生成用于观察随机性；同一素材的改写仍属于同一任务簇，不能扩充成大量独立样本。报告中的不确定性依据已声明的簇解释，不能据此假定案例是总体的随机抽样。

方案冻结文件可以检测随后内容是否变化，但它只是本地一致性记录。开发者仍能在冻结前挑选有利问题，因此外部可信结论还需要独立留出任务、真实使用者、看不到条件的评审，以及对筛选过程的披露。时间戳和哈希不能代替这些条件。

## 初版产品组成与选择

1. 一个宿主可发现的 `assess-value` 技能，引导设计、审核和解释。
2. 一个 Python 标准库本地评估器，读取显式方案与运行账本，生成可携带报告。
3. 一个 Claude 原生评估适配层，用来准备任务和接收结果。导出不等于执行，导入也不自动补全原生结果没有提供的字段。
4. 一组科研审阅教学任务，以及评估本插件是否会过度宣称价值的原生案例。

本地运算的选择降低了安装与依赖成本，也使数据处理逻辑可检查。初版不主动调用外部模型，不自动安装被测插件，不改动用户的插件市场，不提交或发布评估结果。评估者可以自主选择实际执行宿主；任何真实费用、外部数据传输和副作用遵循用户的任务授权。

## 下一阶段什么证据才值得补

产品路线应从暴露决策错误开始：它能否识别一个高分但零增益的插件；是否能抓住平均分提升下的关键退步；是否会诚实保留不完整的原生导入；报告是否让评审者找到具体失败案例。局部软件测试可以检验这些行为。

下一步是用不同插件和真实任务运行独立的有/无插件比较，预先记录判据，保留失败与人力成本，并让实际用户判断报告能否改变决策。科研方向还须验证审阅的假阳性、有效结果保留率、争议解决成本和研究者控制权。完成这些工作之前，合适的定位是**可运行的评估工具原型**，而不是已经证明有效的通用价值裁判。

## v0.2：与 Plugin Management 互补

Plugin Management 已经承担发现外部能力、建议连接、查看依赖以及处理明确管理请求的职责。重新建立一个候选目录会增加用户要记住的入口，也不能替代当前宿主的连接状态。因此本版本增加两项相邻能力：任务开始时给出简单的使用路线；比较结束后把原始证据转化为有适用范围的使用卡。依据与实例见 [互补指南](PLUGIN-MANAGEMENT.zh-CN.md)。

`use-plugin-well` 判断现有能力是否足够，普通工作可以直接继续；需要外部能力时，交接公开关键词与准确插件对象。`assess-value` 只在用户确实要比较或解释证据时进入研究流程。已安装、已启用、已连接和适合当前任务分别记录；过期或不可信的就绪声明要核验，等待中的请求不重复建议。Plugin Management 不可用时可以交给宿主，本地功能不依赖它的私有实现。

连接给用户带来独有的数据访问，是一种实际能力，但不能直接解释成推理质量提高。质量与效率试验应让两组获得同一份授权快照；无法做到时，评价问题转为访问能力并保留归因限制。使用卡则从 suite 与原始运行重新计算，以记录摘要、具体任务、插件版本和执行条件约束建议。模拟、证据缺失或退步会阻止正向使用建议；任何评分都不会授予安装、扩权或卸载的权力。

这项设计希望降低选择和采用负担，目前仍是产品假设。判断是否成功，需要真实宿主任务中的选路准确性、任务完成率、重复建议情况、人工纠正和完整成本；本地自动检查只能证明对应的分流与限制行为。
