# 过程、结果和使用建议的统一门槛

修订目标来自评分机制问题，以及本地审阅材料中 O1、O2、O4、M1–M3、M5–M6 的制造反例。实际修复位于当前源码，不直接采用候选实现。版本保持 0.7.0；不增加宿主工具、评分器种类或 CLI 命令。

## 分数与成功分开

`score` 继续是 outcome 判据的加权分数，用于展示 WITH、WITHOUT 和差值。process 判据始终 `scored: false`；无论权重多大、是否通过，都不进入分子、分母或结果证据层。

每次重算增加 `task_outcome`：

- `layers.decision`：是否作出正确的允许/拒答决定；决策正确不等于交付或结果正确。
- `layers.delivery`：是否交付了满足冻结交付要求的产物。存在 `artifact_schema` 时使用独立结构检查，错误答案不抹去“已经交付”的事实。
- `layers.correctness`：是否通过冻结的任务结果检查。结构合法不能覆盖数值、标签或其他正确性失败。
- `passed` 与 `status`：结合完成状态、质量底线、关键检查和观测可比较性，分别为 true/PASS、false/FAIL、null/UNKNOWN。

必要检查按集合合取，失败优先于未测；在没有已知失败时缺失保留 UNKNOWN。每个运行独立构造状态，评分器顺序、另一组的结果或另一重复不会污染当前运行。运行未完成不能靠一份看似正确的产物被判成功。关键过程检查失败或未知仍阻断比较；非关键过程检查失败/未知保留在明细中，不会被算作结果分。

例如决策与结构通过、冻结的数值检查明确失败，分数仍可能是 2/3；即使执行前将 quality_floor 定为 0.6，也只能保留这个部分分数，任务成功仍为 FAIL，每成功成本为空，不能推荐使用。决策通过但交付/正确性未测则为 UNKNOWN，而不是 0% 已知失败。

## 套件中的任务定义

默认根据冻结的评分器类型确定证据范围，不解析提示中的自然语言来猜“任务是否完成”。`over_refusal` / `abstention_correct` 只提供决策证据；`artifact_schema` 只提供交付证据；`backend_identity` 不提供任务结果证据。已有任务产物校验器和人工/精确结果判据仅证明所写的冻结判据，不认证科学有效性。

旧的纯 `contains` / `not_contains` 套件保留原有加权质量底线和关键检查的接受标准，明确标记为 `configured_checks`。文字检查依然不证明语义正确；不能把通过文字教学套件称为科学验证。加入任务型产物/决策检查后使用分层任务门槛。仅有决策结果判据且 kind=abstention 的旧用例保留纯决策任务语义。

可在 case 元数据中明确冻结：

```json
"success_contract": {
  "version": 1,
  "mode": "task",
  "decision": ["decision"],
  "delivery": ["delivery"],
  "correctness": ["correctness"]
}
```

每一列引用现有 outcome 评分器；过程判据不能充当任何结果层，结构判据不能充当正确性。引用是额外必要条件，不会通过空列表删去已有任务结果检查。没有测量 delivery/correctness 的 task 可以保存，但其成功不得自动变为 true；预检会给出缺失提示。

合法纯决策任务可使用 `{"version":1,"mode":"decision"}`。例如只要求在缺少证据时返回 withhold，正确且可比较的 `abstention_correct` 就能构成该决策任务的成功；交付和数值正确性标记不适用，不伪称已经交付数值结果。具有任务产物评分器的用例不能用 decision mode 绕过它们。此字段属于冻结套件，修改后旧锁与旧观测不再匹配。目录格式完整保留该字段。

## 同一个成功定义流向所有出口

1. 成功数、未知数、paired rescue/harm 使用同一运行状态。
2. `cost_analysis.arms[*].successful_outcomes` 与 value_metrics 成功数一致。新增 `success_unknown`；零成功或尚有未知时不输出每成功成本。总成本仍包含所有失败与未成功尝试。
3. 单组每成功成本是该组已知提交记录的描述值；跨组节省指标仍要求比较成立。未知成本不变成零。
4. 全研究 PROMISING_LOCAL_SIGNAL 除原来的质量、成本、回退条件外，还要求全部 WITH 运行满足任务成功。因此高平均分不再遮住少数未通过运行；`summary.task_success_gate_met` 单独呈现。
5. 单案例、使用范围和 conditional guidance 检查实际所推荐组的成功门槛。已知结果失败或未知，不能只凭分数高于更差的基线获得 LIMITED_TRIAL / use_when。
6. 预先冻结的完整局部范围仍可独立评估；保留原全研究观测、身份问题与共享成本，不删除坏结果重算。修订比过去更保守：没有完整成功证据时留在复核阶段。
7. 可选多端点解释保留执行可靠性、实际交付和冻结正确性检查的区别；仅成本缺失不会抹去已经观测到的产物证据。

HTML / Markdown 报告直接显示各结果层和任务成功；使用卡保留失败与未知的原因及下一步检查。旧存档不会自动改写；重新计算必须保存为新结果，并与旧引擎判断区分。

2026-09-28 补充：总评质量、门槛与区间统一使用冻结的 `policy.quality_weighting`（case 默认／family 可选），另一口径仅作敏感性检查。`decision_review` 区分单次结果、本地受控试用线索与广泛采用；本轮没有放宽全部 WITH 任务成功条件。失败预算必须另有领域依据且事前冻结。详见 [P1 交付](P1-DELIVERY-20260928.zh-CN.md)。

## 验证策略

`tests/test_outcome_contract.py` 使用真正的冻结、文件哈希、产物评分、成本、使用卡和报告路径，覆盖：

- 决策+过程通过但没有交付；只有 schema、没有正确性；错误数值仍高于质量底线。
- 六种评分器排列与两组状态独立；关键与非关键过程检查失败/未知。
- 正确零值、false、空字符串/容器、明确要求的 null；合法纯拒答的正对照。
- 缺产物保留未知；执行失败不被正确产物覆盖；修改成功契约导致锁失配。
- 每成功成本、范围推荐、独立交付/正确性端点以及 HTML/Markdown 展示。

制造数据中的 local/manual 标签仅为触发真实代码中的推荐门槛，不是实际宿主运行或人工观测。通过这些检查证明本地实现行为；不证明科学有效性、真实增益、外部采用或真实作者效率。
