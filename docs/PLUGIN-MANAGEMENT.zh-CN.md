# 与 Plugin Management 配合：把合适的能力用在合适的任务上

Plugin Management 帮助用户找到、连接和管理能力；Plugin Value Lab 帮助用户判断任务是否需要这些能力，以及已有证据支持怎样使用。两者组合的目标是减少寻找、配置和判断的负担，让用户完成眼前工作。

这里的配合通过宿主和可检查的本地计划实现。Value Lab 没有调用 Plugin Management 私有接口，没有把它设置成强制依赖，也不会因为生成了计划就声称插件已经连接。没有 Plugin Management 时，本地评估和使用卡仍然可用。

## 对 Plugin Management 的理解

本次依据已安装的 [Plugin Management 技能原文](C:/Users/13264/.codex/plugins/cache/openai-curated-remote/plugin-management/0.1.0/skills/plugin-management/SKILL.md)、宿主暴露的实际工具契约，以及 2026-09-22 的依赖查询结果整理。可在宿主中查看 [Plugin Management 插件](plugin://plugin-management@openai-curated-remote)。这些来源的适用范围不同：技能规定助手的操作策略，工具契约规定允许的输入与动作，单次查询只描述当时查询到的状态。

它的关键设计并非鼓励多装插件，而是先选择直接可用的能力：原生工具足够时先使用，已连接插件可以完成时直接使用，只有缺少有实际用途的外部能力时才搜索。用户不必先说“插件”；一个需要邮件、日历或外部文档的任务就可能触发发现过程。用户点名某个服务时，具体选择仍应得到尊重。

发现只是开始。搜索使用简短的服务名或能力关键词；建议使用搜索返回的准确标识，并控制在小范围，通常不超过三个。已安装或正在等待连接的插件不应反复建议。建议不会阻塞其他工作，实际调用则需要确认各个插件的连接状态。

生命周期方面，它支持查看特定插件的依赖与权限，以及执行用户明确要求的权限变更和移除。这些是账户动作，不能由评估分数授权。当前权限工具以一个明确的 ChatGPT 插件为对象；“Google”“所有插件”或“我的插件”不能替代准确目标。本地 Claude/Codex 代码插件也不能套用 ChatGPT 应用的权限和移除接口。

本次只读依赖查询显示，当前宿主的 Plugin Management 已安装且用户已启用，依赖列表无未解析条目。这个结果不证明其他插件已经连接，也不代表完整工作流验收。还观察到本地声明把一个 app 标为 `required: true`，而宿主返回的相应依赖标为 `optional: true`；两者属于不同来源的契约，不应合并成“所有宿主都存在同一强制依赖”的结论。宽泛搜索名称还曾返回不相关结果，因此“搜到了结果”也不能替代确认目标身份。本次没有查询账户权限、变更权限或移除插件。

## 分工与交接

| 用户实际问题 | 主责 | Value Lab 提供什么 |
| --- | --- | --- |
| 这项工作现在用什么最省事？ | Value Lab 指导，宿主执行 | 判断现有能力是否足够；给出简短使用建议 |
| 缺少一个日历、文档或数据源连接怎么办？ | Plugin Management 或宿主 | 交接最少的公开能力关键词，不发送完整任务材料 |
| 这个插件是否已连接、需要哪些依赖？ | Plugin Management 或宿主 | 记录查询来源和时效，保留未知状态 |
| 请查看或修改这个插件的权限，或把它移除 | Plugin Management 或对应宿主 | 只按明确目标与用户请求交接；分数不授权账户动作 |
| 使用插件是否提高质量或节省完整成本？ | Value Lab | 设计匹配比较、检查原始记录、保留失败和不确定性 |
| 已经测过，哪些任务该用、哪些任务基线足够？ | Value Lab | 从记录重新计算，生成有适用范围的使用卡 |

这种分工保留了两种独立判断：**能力可达性**回答能否取得所需数据或执行所需动作；**任务增益**回答在可比较条件下是否做得更好。连接成功不能自动回答后者，零增益也不能说明连接毫无用途。

## 三个常见场景

### 1. 眼前任务：整理一段已经提供的文字

用户说：“把这段会议记录整理成三条待办。”如果现有能力足够，直接完成即可。无需搜索插件、安装评估器、检查权限或启动双组试验。Value Lab 在这里最有用的行为是减少步骤。

对应示例是 [native-sufficient.json](../examples/workflows/native-sufficient.json)。运行后得到一个本地计划；计划表达 `USE_NATIVE` 的建议，并不替用户执行原任务。

```powershell
python scripts/value_lab.py plan-use .\examples\workflows\native-sufficient.json --output .\work\native-plan
```

### 2. 缺少外部能力：安排需要读取日历的会议

用户说：“根据我的日历找一个空闲时段。”先检查已有能力是否可以访问日历；确实缺少时，向 Plugin Management 交接 `calendar availability` 这样的公开关键词。无需把私人日程、参会者名单或完整对话发送到发现服务。查到相关候选后，宿主可以建议连接最小集合，并继续准备不依赖连接的会议要求。

对应示例是 [missing-calendar.json](../examples/workflows/missing-calendar.json)。它声明当前能力不足，输出发现路径；并未证明用户真实账户的当前状态，也不会发起搜索或连接。

若宿主刚确认候选仍在等待连接，提示一次剩余动作即可，继续独立准备，不重复建议、不把“已安装”说成“已连接”。[stale-connection.json](../examples/workflows/stale-connection.json) 展示另一种常见情况：手头只有历史就绪记录，必须先核验当前状态。这个虚构教学对象不指向真实服务，其固定旧时间戳故意不会被当成当前连接证明。

### 3. 长期采用：批量文档审阅是否值得使用插件

用户说：“以后每周都要审阅这些文档，这个插件是否值得固定使用？”此时更适合一轮预先设计的比较：明确质量底线，选入普通任务、插件可能无额外帮助的任务，以及需要保留不确定性的任务；冻结条件后收集两侧结果与完整成本。

如果插件的主要优势是读取一个基线无法访问的文档系统，先说明这是访问能力。可以单独评估检索成功、材料完整性和人工搬运成本；要比较推理或审阅质量，两侧应得到同一份经授权的数据快照。不能让有插件侧读完整文件、基线侧只看摘要，再把差异写成推理提升。获准读取不代表获准把材料复制到另一个外部服务；无法获得同等授权时保留比较限制。

已有 suite、运行记录和锁文件时，可以生成使用卡：

```powershell
python scripts/value_lab.py usage-card .\work\my-study\suite.json .\work\my-study\runs.jsonl --lock .\work\my-study\protocol.lock.json --output .\work\my-study\usage
```

卡片从原始记录重新计算，输出适合使用的已测任务、基线可能足够的任务、需要调查的情况和下次需要更新证据的变化。不是把一份任意正向报告换成推荐语。若记录为模拟、缺失关键证据或出现退步，就只给试用或复查指导，不生成正向使用建议。插件版本、模型、宿主、工具、配置、任务或数据变化时，应重新检查原结论是否适用；这不自动创建监控任务。

## 让用户少记概念的两种入口

- “这项任务该用什么能力？”或“这个插件怎么用更合适？”进入 `use-plugin-well`，先完成任务，必要时生成计划。
- “比较这个插件与基线的收益”或“解释这份评估结果”进入 `assess-value`，处理比较设计与证据。

“帮我连接一个日历插件”或“请移除指定插件”仍由 Plugin Management／宿主管理流程处理。Value Lab 不抢占这些触发，也不引入一个与宿主目录竞争的插件排行榜。

一次性问题通常只需几句话；助手从自然语言任务和真实宿主观察构造上下文，不要求用户填写 JSON 或记住状态码。本地文件用于需要复查、分享或接续的决定。CLI 的 `plan-use` 输出 `PLAN.md` 与 `plan.json`，`usage-card` 输出 `USAGE.md` 与 `card.json`。MCP 分别提供 `plan_plugin_use(context)` 与 `build_plugin_usage_card(suite, records, lock)`，仅在宿主实际暴露这些工具时使用。管理请求的交接还保留明确动作及所请求的权限模式，不携带完整私有任务；这些模式本身也不证明服务的 OAuth 数据访问范围。

## 科研示例：把访问材料与判断证据分开

研究者希望审阅一份多供体差异表达交付物。Plugin Management 可以帮助发现并连接研究者授权的文件来源；是否找到连接，与交付物是否有合格的供体重复无关。Value Lab 可以比较使用审阅插件后，错误接受是否减少、有效结论是否保留、争议处理与人工复核成本是否合理。

两组必须获得相同的授权材料，科研正确性仍由实际领域评审者依据原始证据判断。目录状态、连接回执、卡片、软件测试或模型评分都不能成为独立科学验证。[科研教学 suite](../examples/scientific-suite.json) 仍是虚构教学材料，不能为真实插件收益背书。

## 当前证据边界

本地计划与使用卡支持可复查的软件行为，尚无真实用户研究证明组合能降低学习成本或提高持续使用收益。本次只读查询也不等于安装后的双插件端到端验收。后续应在实际宿主记录：是否选对能力、是否避免重复建议、是否把未知连接状态保留为未知、是否完成用户任务，以及是否让用户更容易决定下一步。

发现效率、账户管理行为、任务结果和科学判断分别需要各自证据。不要把它们合成一个无法解释的“插件价值总分”。
