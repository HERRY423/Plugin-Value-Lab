# v1.0.0-rc.1 候选发布交付与四项严谨性规范 / Candidate Release Delivery & Four Rigor Pillars

## 概述 / Overview

2026-10-03，按用户明确要求发布 `v1.0.0-rc.1` 候选版本。本项目（Plugin Value Lab）旨在以严谨、可复算、防伪造的科学评测框架，对大模型插件的真实任务增益进行两臂对照评估。

本候选发布版本冻结了候选提交代码与分发安装包（Python Wheel 包、ChatGPT 市场 ZIP 包、通用 Agent 插件 ZIP 包），完成全套 CI 门禁核验与隔离环境安装验收，并正式确立科学评估的**四大严谨性支柱（Four Rigor Pillars）**：
1. **真实两臂隔离（True Two-Arm Isolation）**
2. **完整工具清单（Complete Effective Tool Inventory）**
3. **原始产物封存与重新评分（Raw Artifact Preservation & Local Re-scoring）**
4. **断线／取消／重试的原尝试对账（Attempt Journal Reconciliation for Disconnect, Cancellation, and Retry）**

## 三、四大严谨性支柱详述 / The Four Rigor Pillars

### 支柱一：真实两臂隔离（True Two-Arm Isolation）

对照研究（WITH vs. WITHOUT）的核心前提是两臂在任务执行时处于绝对干净、相互独立的评估环境中。
1. **全新会话与请求身份（Fresh Session & Request Identity）**：
   - 每次任务尝试必须声明并核验为全新的干净会话：
     - `context.fresh_session: true`
     - `context.prior_messages: 0`
     - `context.parent_session_id: null`
     - `context.memory_enabled: false`
     - `context.shared_artifacts: false`
   - 全局会话去重：`session_id` 与 `request_id` 严禁在多次尝试、多任务或两臂之间跨越复用。任何重复 ID 均作为上下文污染立即标记为非法（fail-closed）。
2. **两臂暴露严格受控**：
   - **WITH 臂（实验臂）**：
     - 必须且仅允许暴露冻结计划中指定的候选插件（`plugins` 列表长度必须为 1，且插件 ID、版本与 SHA-256 必须与冻结计划完全吻合）。
     - 工具集严格等于：公共基础工具集（`common_tools`）+ 候选插件工具集（`candidate_tools`）。
   - **WITHOUT 臂（基线对照臂）**：
     - 严格保持零候选插件暴露（`plugins: []`）。
     - 工具集严格等于公共基础工具集（`common_tools`），绝对不得出现任何候选插件提供的工具或其变形版本。
3. **上下文摘要密码学锁定**：
   - 运行环境必须校验上下文配置的 SHA-256 摘要（`context_sha256`）与冻结计划的预期值一致，杜绝任何隐式系统提示词（system prompt）注入或临时参数篡改。

### 支柱二：完整工具清单（Complete Effective Tool Inventory）

为了杜绝“隐形工具介入”或“假装没有工具实际存在隐式工具”，系统引入宿主生效工具清单校验机制。
1. **宿主生效清单凭证**：
   - 清单来源必须标明为真实宿主生效清单：`source_kind: "host_effective_inventory"`。
   - 必须显式声明清单完整：`inventory_complete: true`。
   - 严禁任何形式的未处理分页、截断或模糊状态：`has_more: false`、`truncated: false`、`next_cursor: null`，否则拒绝采信。
2. **工具定义指纹锁定（Definition Digest Pinning）**：
   - 清单中的每一项工具，不仅要求提供唯一的名称，还必须计算并提交其完整 Schema 定义（含参数说明、类型限制与工具描述）的规范 JSON 序列化 SHA-256 摘要（`definition_sha256`）。
   - 系统将实际生效的每个工具的名称及摘要，与冻结时计划定义的工具集进行双向精确比对。任何工具的缺失、多余、改名或 Schema 变动均判定为环境偏离，拒绝作为有效证据。

### 支柱三：原始产物封存与重新评分（Raw Artifact Preservation & Local Re-scoring）

科学评估拒绝“口头报告通过”或“黑盒判定”。
1. **原始 UTF-8 文本完整封存（Verbatim Raw Output）**：
   - 每次尝试的输出必须保留最原始的文本形式（`raw_output`），保持 UTF-8 编码原生字节。
   - 禁止在进入评分前对输出进行摘要化、截断、预过滤或语义润色。若某次尝试无输出（如崩溃或超时），必须显式给出 `null`，字段不得缺省。
2. **密码学生成绑定**：
   - 原始输出必须计算并绑定 `output_sha256 = sha256(raw_output.encode("utf-8"))`。
   - 所有后续派生的分析产物、指标计算与审计追踪必须关联此哈希。
3. **本地客观重算评分（Local Deterministic Re-scoring）**：
   - 评分器必须基于 `raw_output` 或从中解包出的实际产物文件在本地重新运行打分算法（正则匹配、AST 语法树分析、JSON Schema 验证、科学计算产物校验等）。
   - **零信任原则**：绝不信任外部宿主上报的 `pass`/`fail` 标志，绝不采信大模型在回复中自称的“任务已成功完成”等无凭据断言。所有打分逻辑均可在离线环境下根据原始输出完全重现。

### 支柱四：断线／取消／重试的原尝试对账（Attempt Journal Reconciliation）

面对网络抖动、宿主崩溃、任务超时或用户取消等现实工程扰动，必须有坚固的状态追踪与对账机制，严防统计偏差。
1. **SQLite 本地持久化日志（AttemptJournal）**：
   - 采用不可篡改的 SQLite 结构化日志表（具备触发器防止历史行被更新或删除），按冻结计划的 `plan_sha256` 独立绑定。
   - 全生命周期状态机：
     - `prepared`（准备预留）→ `dispatched`（已发出请求）→ `running`（宿主执行中）→ 终态。
     - 终态包括：`completed`（完成）、`failed`（失败）、`cancelled`（取消）、`unknown`（未知/断线）、`not_dispatched`（未真正发出）。
2. **断线与未知状态回溯对账**：
   - 若通信中断或宿主失去响应，尝试转为 `unknown` 状态。
   - 系统禁止简单丢弃 `unknown` 尝试；必须通过操作员提供的真实外部凭证（`source_ref`，如宿主原始事件日志、账单编号或网络响应收据）向原始尝试进行回溯对账（reconciliation），完成状态定性。
3. **分母守恒与意向性分析原则（Denominator Conservation / Intention-to-Treat）**：
   - 凡是一旦发出的尝试（`dispatched`），不论最终遭遇取消（`cancelled`）、网络断线（`failed` / `unknown`）还是执行失败，**必须一律保留在有效样本量分母中**。
   - 严禁剔除失败或中断样本只保留成功案例，彻底杜绝幸存者偏差（Survivorship Bias）。
4. **显式诊断重试与首次尝试首要性（Primary Attempt Permanence）**：
   - 重试不是静默重跑：必须通过 `reserve(slot_id, idempotency_key, retry_of=primary_attempt_id)` 显式发起，且仅允许在原尝试已处于明确终态（`failed`、`cancelled`、`not_dispatched`）时进行。
   - **首次尝试永久作为主效应指标依据**：在正式的确认性检验（Confirmatory Evaluation）与统计推断中，样本的最终得分始终以首次尝试（Primary Attempt）为准。重试结果仅作为次要诊断/探索性参考，重试成功绝对不能篡改、覆盖或抹去首次尝试的失败记录。
5. **全量费用与负担结算对账（Full Cost Reconciliation）**：
   - 账本必须核算所有尝试（包括重试、超时、取消和失败尝试）产生的模型 Token 消耗与供应商账单金额。
   - 报告在计算插件带来的时间与成本负担时，必须采用包含所有尝试的全口径累计费用（`settled costs`），避免低估插件在现实不稳定网络下的隐性开销。

## 四、真实边界与限制声明 / Limitations & Boundaries

1. **宿主执行认证边界**：
   - 本地日志与捕获合同（`codex_evidence.py`、`attempt_journal.py`）提供严密的结构化防篡改约束，但操作员捕获（`operator_capture`）在未建立受信任密码学远程认证前，仍依赖提交凭证的完整性声明。
   - 合成数据（`synthetic`）与测试用例（`SIMULATION_ONLY`）仅用于验证流水线与算法鲁棒性，不可作为真实插件具有优越性的科学结论证据。
2. **无自动付费与外部依赖保持**：
   - PVL 自身不内置任何未经用户许可的自动付费通道或外部 API 调用凭证，预算守卫继续强制阻断无上限请求。
3. **接口稳定性承诺**：
   - 本次候选发布保持主 CLI 黄金五步命令、六个默认 MCP 工具签名以及面向集成者的公开 Python SDK 完全兼容与冻结，满足工程生产要求。
